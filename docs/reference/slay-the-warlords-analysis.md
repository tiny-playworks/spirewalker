`output/playwright/slay-the-warlords/`

## 一、体验路径

### 1. 首页与角色选择

首页首先给出语言切换、版本信息和进入游戏入口，视觉焦点集中在中央主入口，没有用过多系统信息干扰开始游戏。

![首页](../../output/playwright/slay-the-warlords/01-home.png)

进入主菜单后，主要操作被组织为出征、继续征程、每日挑战、图鉴、设置和退出。角色选择页展示多个角色、角色定位、被动能力和生命信息；玩家在开始地图前已经能建立“我是谁、这个角色怎么赢”的初步预期。

![角色选择](../../output/playwright/slay-the-warlords/03-character-select.png)

### 2. 地图与路线

地图页展示当前幕、当前层、路线节点、路线连接和节点图例。首个可选节点被明确突出，选择后能看到路线关系，再进入下一页面。

![地图](../../output/playwright/slay-the-warlords/04-map.png)

实际体验路线为：地图入口战斗 → 战斗奖励 → 后续战斗 → 多敌人战斗 → 商店 → 战斗 → 失败结算。

### 3. 一场完整战斗

第一场战斗完整观察了以下循环：

1. 敌人展示当前意图和状态。
2. 点击手牌中的单体卡牌进入目标选择。
3. 敌人出现目标高亮，其他区域降低干扰，卡牌进入选中状态。
4. 目标选择后，画面出现实时结算预览。
5. 出现伤害、格挡、资源变化和状态变化反馈。
6. 点击结束回合，敌人执行意图并进入下一回合。

![战斗开始](../../output/playwright/slay-the-warlords/05-battle-start.png)

![卡牌目标选择与预览](../../output/playwright/slay-the-warlords/06-card-target-preview.png)

![攻击结算](../../output/playwright/slay-the-warlords/07-attack-result.png)

### 4. 多敌人、目标选择与敌人意图

第三场战斗包含多个敌人。卡牌选中后，每个可选敌人都能成为独立目标；目标区域有明显高亮，目标的生命、意图和状态仍然可读。

![多敌人战斗](../../output/playwright/slay-the-warlords/12-multi-enemy-battle.png)

![多目标选择](../../output/playwright/slay-the-warlords/13-multi-target.png)

敌人意图由图标、数字和文本共同表达。对意图进行查看时，能够看到从基础效果到修正项再到最终结果的解释。状态效果使用图标、层数和提示信息表达；玩家和敌人的格挡、虚弱、仪式等状态在战斗中都能持续观察。

![敌人意图与状态](../../output/playwright/slay-the-warlords/09-enemy-intent-status.png)

### 5. 战斗奖励

战斗结束后进入独立奖励页，奖励页明确显示胜利、金币、卡牌选择、跳过奖励的替代收益，并提供继续前进入口。实际操作中选择一张卡后，牌组规模和奖励内容可以被继续确认。

![战斗奖励](../../output/playwright/slay-the-warlords/10-battle-reward.png)

继续后回到地图，当前层数和下一步路线保持连续，没有把战斗奖励做成孤立的弹窗。

![奖励后的地图](../../output/playwright/slay-the-warlords/11-map-after-reward.png)

商店将卡牌、遗物、消耗品、升级和删牌分成不同区域，价格与当前金币同时可见。购买后商品变为售罄，金币和牌组数量同步变化；买不起的商品会被禁用，并显示还差多少金币。

本次没有直接结束新局，而是在进入后续战斗后主动结束回合，观察生命归零后的失败结算。结算页包含失败原因、停止层数、击败敌人、累计伤害、最高单次伤害、金币、最终卡组、卡牌贡献、路线回顾、挑战种子和重新开始入口。

![失败结算](../../output/playwright/slay-the-warlords/20-failure-settlement.png)

展开后还能查看完整卡组构成，以及没有打出过的卡牌。这使失败从“结束提示”变成了下一局可复盘的反馈。

![失败结算中的卡组详情](../../output/playwright/slay-the-warlords/21-failure-deck-detail.png)

### 8. 事件与休息点的验证边界

本次固定路线实际进入了商店，没有在竞品页面中额外进入事件或休息点，因此不对竞品事件/休息点的具体交互下结论。Spirewalker 当前的事件和休息页面已通过源码只读核对，相关对照与后续验收标准会单独标记为“待真人浏览验证”。

## 三、核心战斗循环如何建立反馈

竞品战斗的强项不是单个动画，而是把每个行动拆成连续的反馈链：

`意图 → 行动选择 → 目标确认 → 结果预览 → 资源/状态结算 → 敌方回应 → 下一回合意图`

这条链同时提供了三种信息：

1. **预期**：敌人打算做什么，卡牌可能带来什么结果。
2. **确认**：当前选中了哪张牌、哪个目标，操作是否已经被系统接受。
3. **结果**：生命、格挡、资源、状态、手牌和弃牌区如何变化。

其中最值得借鉴的是“选择目标后再给一次实时预览”。它把玩家的犹豫点放在结算前，降低了误点和规则不透明带来的挫败感，也让单体卡、群体卡和状态卡能用同一套操作语言表达。

Spirewalker 当前已经具备部分基础：`ReactBattleStage` 支持卡牌点击、拖拽、敌人目标按钮、选中态、动画锁和固定在底部的结束回合按钮；`EnemyPanel` 也有意图文本和状态提示。但当前 `cardFocus` 主要从卡牌定义中估算伤害/格挡，尚未形成覆盖实际规则修正、目标状态和遗物影响的统一结算预览。因此未来应优先补“真实规则驱动的预览协议”，而不是只增加装饰动画。

## 四、页面信息层级与视觉焦点

### 竞品的层级

桌面战斗页面大致分成四层：

1. **全局状态层**：生命、金币、幕/层、遗物和物品栏。
2. **战场决策层**：玩家、敌人、敌人意图和状态。
3. **行动层**：手牌、能量、抽牌堆、弃牌堆、消耗区。
4. **辅助解释层**：卡牌描述、状态提示、牌组、规则和菜单。

视觉焦点始终在“敌人将做什么”和“我现在能做什么”之间切换。奖励页、商店页和结算页则把一个核心决策放在中央，其余信息退到侧栏或辅助面板。

### 对 Spirewalker 的启示

Spirewalker 当前页面已经有比较完整的模块划分，但需要继续收紧“首要动作”：

- 战斗顶部的能量值目前在 `title` 中提供完整信息，视觉上只显示能量图标；这对鼠标悬停友好，对触控和快速决策不够直接。
- `RunOverviewPanel`、牌组、遗物和菜单都有能力提供信息，但在手机尺寸下需要保证辅助面板不会遮住手牌、目标和结束回合。
- 地图已经自动把当前节点滚动到可见位置，且支持图例折叠、下一节点选择和路线预览；下一步重点是让“当前节点、可选节点、危险节点、下一步结果”在移动端也能同时读懂。
- 失败和通关页当前仍是轻量提示，无法承接一局游戏积累的统计和路线信息，是信息层级中最明显的断层。

## 五、卡牌尺寸、排布与交互

### 浏览器实测

- 桌面手牌采用扇形排列，卡牌之间有重叠但仍保留名称、费用、类型和效果说明的阅读入口。
- 卡牌可点击；需要目标的卡牌点击后进入选择目标状态。
- 卡牌可拖拽到目标区域，拖拽与点击目标使用的是同一个“选择卡牌 → 选择目标”的心智模型。
- 选中的卡牌有明显的状态变化；可选目标出现高亮，非目标区域被弱化。
- 结算后卡牌从手牌移除或进入对应牌堆，资源数字和浮动反馈同步更新。
- 卡牌、遗物、状态都有可查看的提示信息；规则页提供更完整的解释。

### 对 Spirewalker 的建议

保留 Spirewalker 自己的卡牌视觉和 Walker 语义，重点借鉴以下交互协议：

```text
默认态 → 悬停/按下 → 选中卡牌 → 可选目标高亮 → 结算预览 → 执行 → 结果反馈
```

桌面端可以继续使用扇形手牌和拖拽；移动端不应依赖拖拽才能完成战斗，应保证“点卡牌、点目标”完整可用。卡牌不能因为扇形或容器高度被裁切；结束回合应与手牌在同一个稳定的可见区域中。

## 六、敌人意图、伤害预览与状态效果

### 敌人意图

竞品将敌人意图做成战斗的第一决策信息，而不是附属装饰：图标表达动作类别，数值表达量级，文本说明动作方向；查看提示时还会解释修正过程和最终结果。

Spirewalker 已在 `ReactBattleStage` 中给敌人目标按钮设置意图文本，并在状态芯片上提供提示；下一步应把这些信息从“可查看”提升到“默认可读”：

- 关键意图的动作和数值在不依赖悬停时可见。
- 选中卡牌后，预览应根据目标、当前状态、Walker、Momentum、遗物和卡牌升级实时计算。
- 状态图标、层数、持续时间和触发条件要有统一的提示入口。
- 敌人回合结算时，意图执行、伤害、格挡和状态变化要分出先后，避免所有数字同时跳出导致玩家无法归因。

### 伤害与状态反馈

竞品使用生命条变化、浮动数字、格挡变化、状态图标和文本提示叠加反馈。建议 Spirewalker 将反馈分成三档：

1. **战场即时反馈**：伤害、格挡、治疗、资源变化。
2. **状态反馈**：获得、消耗、叠加、减少和触发原因。
3. **可回看反馈**：战斗日志或结果摘要，供玩家确认复杂连锁。

这三档应该共享同一领域事件，而不是由各个 React 组件分别猜测发生了什么。

## 七、地图、奖励、商店和事件的衔接

### 竞品实测到的衔接

- 地图选择后立即进入目标页面，页面顶部仍保留幕/层和资源上下文。
- 战斗奖励不是瞬间消失的浮层，而是一个独立决策页。
- 奖励完成后通过明确的继续按钮回到地图，下一节点继续突出。
- 商店把购买、升级、删牌和离开集中在一个页面，购买后金币、库存和牌组即时更新。
- 牌组和规则可以在关键决策页被打开，玩家不需要退出当前路线去记忆卡牌信息。

### Spirewalker 当前对照

Spirewalker 的 `MapPage` / `MapRoute` 已有当前节点自动定位、下一节点限制、图例折叠、节点二次确认和路线预览；`RewardPage` 已有卡牌、金币、遗物、药水和升级入口；`ShopPage` 已有卡牌、遗物、药水、升级和删牌；`EventPage` 已有选项禁用条件；`RestPage` 已有生命恢复提示。

当前更需要统一的是“结果确认”和“返回地图”的节奏：事件结果目前直接解析后回到地图，休息点只有一次操作后回地图，奖励/商店也需要确保购买或选择后的变化在用户眼前被确认。所有节点都应遵守：

```text
进入节点 → 展示可做决策 → 执行一次选择 → 展示实际变化 → 明确返回地图 → 突出下一步
```

## 八、动画、音效与操作节奏

### 观察到的反馈

- 卡牌选择、目标选择和结算之间有明确的状态切换。
- 伤害、格挡、资源获得和状态变化使用短暂的视觉反馈，让玩家能把操作和结果联系起来。
- 奖励卡牌和选项按顺序进入页面，避免所有内容同时出现造成突兀感。
- 战斗允许玩家以较短的操作周期完成“选牌—选目标—结算—继续”。

本次自动化浏览环境无法可靠确认音频播放、音效层级或不同音效开关的实际效果，因此不把“竞品音效好坏”写成结论。后续如果要专门比较音效，需要真人浏览器体验和独立的声音检查。

### 对 Spirewalker 的建议

- 先建立领域事件到视觉反馈的节奏表，再补动画和音效。
- 普通反馈要短，关键反馈可以稍长，但不能阻塞连续出牌。
- 复杂连锁按“触发来源 → 中间变化 → 最终结果”播放。
- 快速模式只压缩等待时间，不跳过必要的状态变化和结果提示。
- 音效使用 Spirewalker 自己的声音设计，不引用竞品素材或模仿其具体音色。

## 九、竞品优点

1. **战斗反馈是闭环的**：意图、目标、预览、结算和下一回合紧密连接。
2. **视觉焦点稳定**：战斗看敌我双方和手牌，奖励看奖励，商店看购买决策，页面职责清楚。
3. **交互容错较好**：单体卡牌需要目标时，不会让玩家误以为点击卡牌就已经完成行动；选中态和目标态分得开。
4. **复杂信息可渐进展开**：常用信息默认展示，详细公式、状态词典、完整牌组通过提示或面板展开。
5. **奖励与路线连续**：奖励页不是终点，继续前进后仍然能回到路线判断。
6. **商店交易反馈明确**：价格、当前货币、售罄和不足提示能帮助玩家比较，而不是只给一个不可用按钮。
7. **失败也有价值**：统计、卡牌贡献和路线回顾让失败能够指导下一局。
8. **规则解释完整**：角色资源、状态和关键词有可查阅的解释，不完全依赖玩家自行猜测。

## 十、竞品问题与适用边界

以下是本次体验中值得注意的限制，不代表竞品所有版本和所有设备都必然存在同样问题：

1. 本次只完成了桌面浏览器实测，没有据此判断其移动端适配质量；移动端结论需要单独验证。
2. 复杂公式和状态解释较多，信息密度高。对新玩家而言，需要通过首次引导和渐进提示控制学习成本。
3. 依赖悬停或浏览器提示的细节在触控设备上可能不够自然，因此 Spirewalker 不能把关键规则只放进 `title`。
4. 结算页信息丰富，若没有明确的主行动和分组，可能从“复盘工具”变成“数据墙”。Spirewalker 应优先呈现本局结果和下一步，再提供展开详情。
5. 本次路线没有覆盖竞品事件和休息点，相关体验不应直接推断。
6. 本次没有对长期多局、平衡性、随机路线覆盖率和全部角色做系统测试，不能以单次体验替代数值分析。

| 事件 / 休息 | 本次竞品路线未进入，具体表现不下结论 | `EventPage` 有选项与禁用条件；`RestPage` 有恢复提示和返回地图操作 | 结果变化与返回地图之间缺少统一的可见确认层 | 使用统一节点结果摘要，不允许静默改变状态 |

| 失败 / 通关 | 有统计、卡牌贡献、路线、种子和重新开始 | `App.tsx` 中 `GameOverScreen` 仅显示探索结束，`VictoryScreen` 仅显示试玩通关和两个按钮 | 这是当前最大完成度差距：一局经历没有被总结，也无法指导下一局 | 建立独立结算页，支持失败与胜利两套结果数据 |
| 长期档案 | 竞品实际体验了图鉴、规则和结算关联信息 | `ProfileState`、版本化 localStorage、图鉴、遗物、收藏和成就已经存在 | 长期档案与单局结算的关联还可以更强；内容定义仍有提前加载 | 将结算统计接入 Profile，并按需懒加载大型图鉴内容 |

### 当前最影响完成度的差距

如果只选一个差距，优先级最高的是**战斗和结算之间缺少可复盘的产品闭环**：

- 战斗中，玩家需要知道为什么这一手牌会造成当前结果。
- 战斗后，玩家需要知道这一局走到了哪里、构筑如何变化、哪些卡牌和遗物真正产生了贡献。
- 失败或胜利后，玩家需要有明确的下一步：重试、回主菜单、查看牌组、查看档案或继续进入下一幕。

Spirewalker 的页面数量和系统基础已经不少，下一阶段不应优先继续堆页面，而应把“决策前可理解、执行中可确认、结束后可复盘”接成一条完整体验链。

## 十二、可借鉴项

### P0：直接影响“能不能完整玩通”的通用原则

1. **统一战斗反馈协议**：每次出牌都至少有意图、目标、预览、结算和结果五个状态。
2. **预览必须来自真实规则**：同时考虑卡牌升级、Walker、Momentum、状态、遗物和目标，而不是只把卡牌基础值展示出来。
3. **行动结果必须可归因**：伤害、格挡、资源和状态变化要能对应到触发来源。
4. **结算必须是完整页面**：失败和胜利都显示本局统计、路线、牌组摘要、主要贡献和下一步行动。
5. **节点结果必须可确认**：奖励、商店、事件、休息点执行后，先展示状态变化，再回到地图。
6. **移动端使用点击路径完成全部核心操作**：拖拽可以保留，但不能成为完成战斗的前提。

### P1：影响理解和决策质量的原则

1. 默认突出当前回合最重要的资源、敌方意图和可选目标。
2. 常用信息常驻，复杂解释通过点击或长按展开，不把关键规则藏在鼠标悬停中。
3. 地图同时表达当前位置、可选位置、风险节点和路线后果。
4. 购买、选牌、升级和删牌都显示执行前条件与执行后变化。
5. 规则词典和卡牌/遗物提示共享同一套领域定义，避免 UI 文案与实际效果分叉。

### P2：影响节奏和长期品质的原则

1. 用领域事件驱动动画和音效，保证表现层不改变结算事实。
2. 普通反馈快速完成，关键连锁按因果关系分段播放。
3. 将详细档案、图鉴和大型内容索引懒加载，首屏只加载当前 Act 需要的内容。
4. 结算统计与长期档案关联，让每一局都能为下一局提供信息。

## 十三、禁止照搬项

以下内容不应进入 Spirewalker：

- 竞品的人物、角色关系、三国题材、人物名称、卡牌名称和文案。
- 竞品的具体数值、敌人行为表、奖励结构中的精确参数和概率。
- 竞品的图片、立绘、图标、音频、字体、动画素材及其提取结果。
- 竞品的美术风格、构图细节、颜色组合和品牌识别元素的直接复制。
- 竞品页面的原文案、公式文案、提示文案和菜单命名。
- 以竞品的“角色—卡牌—遗物”关系替换 Spirewalker 自己的 Walker、Momentum 和内容体系。
- 只为视觉相似而复制地图形状、战斗布局或结算页的具体装饰；应只吸收信息层级和交互原则。

可以借鉴的是“状态如何表达、决策如何确认、结果如何复盘”，不能借鉴其具体内容和资源。

## 十六、验收标准

### 产品流程

- 固定种子可以连续跑通：新局 → 地图 → 普通战斗 → 奖励 → 事件/营地/商店 → 精英战 → Act 1 Boss → 进入 Act 2。
- 桌面尺寸 `1280×720` 和移动尺寸 `390×844` 都能完成上述关键流程。
- 地图进入后当前节点和可选下一节点可见，节点触控区足够大，图例不会遮住路线。
- 奖励、商店、事件、休息点完成操作后，状态变化可见，并能明确返回地图。

### 战斗反馈

- 单体卡牌支持点击选牌、点击目标、取消目标和重新选择目标。
- 拖拽是增强操作，不是移动端完成战斗的必要条件。
- 多敌人时每个目标都能独立被选中，目标高亮和不可选状态清楚。
- 敌人意图默认可读；关键动作包含动作类别、结果量级和必要的状态说明。
- 预览结果与实际结算一致，至少覆盖卡牌升级、Walker、Momentum、状态、遗物和多目标效果。
- 结束回合按钮始终可见，不被手牌、弹窗或移动端安全区遮挡。

### 结算与长期状态

- 失败和胜利结算都展示本局基本统计、路线摘要、最终牌组和主要贡献。
- 结算页提供重新开始、返回主菜单、查看档案等明确动作；如果流程允许进入下一幕，提供继续入口。
- `gain_momentum` 统一表示“下一场战斗开局获得 Momentum”，事件获得后下一场战斗生效并清零。
- 实际可获得遗物都有运行时 Hook；遗物、事件和卡牌状态不会跨战斗错误残留。
- 图鉴、成就和统计跨对局保存，版本迁移和清空本地档案可用。

### 工程质量

- TypeScript 检查、Lint、单测、构建和 E2E 全部通过。
- 固定种子 E2E 不依赖屏幕坐标，不存在重复 `data-testid` 或重复可交互桥接元素。
- 新增卡牌、遗物和事件必须同时通过唯一 ID、描述/效果、Hook 覆盖和运行时测试校验。
- 图鉴等大型内容按需加载，首屏包体不超过既有 gzip 基线。

## 结论

《杀戮三国》最值得 Spirewalker 借鉴的不是题材或视觉，而是它把“敌方意图、行动预览、结果反馈、奖励选择和失败复盘”连成了连续的决策体验。

Spirewalker 当前已有地图、战斗、奖励、商店、事件、遗物 Hook、`pendingBattleMomentum` 和长期档案等基础模块。下一阶段最应该做的是把这些模块接成可被玩家感知的完整闭环：战斗前能理解，操作中能确认，操作后能归因，一局结束能复盘。完成这个闭环后，再扩展 Act 2/3、内容数量、声音和性能优化，收益会更高。
